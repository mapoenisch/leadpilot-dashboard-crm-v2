# Release Notes v3.1.0 — LeadPilot Dashboard-CRM

**Version:** `3.1.0` · **Lizenz:** proprietär, **All Rights Reserved** ([LICENSE](../../LICENSE))
**Status:** freigegeben zur Veröffentlichung (Auftrag 142, Plan _CRM-Verbindlichkeit_; annotierter Tag `v3.1.0` auf dem Merge-Commit des Release-PR durch Marc Pönisch).

Release `v3.1.0` macht das operative CRM verbindlich: Was v3.0.0 als Kanban, Qualifizierung und Funnel versprach, wird jetzt dauerhaft in der Datenbank gespeichert und ist für alle Nutzer eines Mandanten gleich sichtbar. Browser-Speicher ist keine Datenquelle für Fachzustand mehr. Alle vier Einschränkungen des v3.0.0-Nachtrags sind behoben.

---

## ⚠️ Vor dem Ausrollen: Migrationen anwenden

**Die Migrationen `20261110_deal_stage_tracking` und `20261111_lead_qualification` müssen auf gehostete Instanzen angewendet werden, BEVOR das neue Frontend ausgeliefert wird.** Ohne sie schlagen die neuen RPCs (`move_deal_stage`, `convert_lead_to_deal`) und die Spalte `stage_entered_at` fehl.

```bash
supabase db push   # oder equivalente Migration der Dateien 20261110/20261111
```

**Zusätzlich muss die Edge Function `crm-query-export` neu deployed werden** (`supabase functions deploy crm-query-export`). Sie wurde in v3.1.0 erweitert und liefert erstmals `stageEnteredAt` und `sourceContactId` — ohne das Deployment bleiben Phasenwechsel im Funnel ohne Verweildauer und die Engpass-Erkennung greift nicht.

## Neu und geändert (Aufträge 136–141)

### 1. Serverseitige Phasenpersistenz (`supabase/migrations/20261110_deal_stage_tracking.sql`)

- Neuer RPC `move_deal_stage`: Phasenwechsel im Kanban und in der Tabelle laufen atomar über Postgres — mit Mandanten-, Rollen- und Konfliktprüfung sowie Audit-Eintrag.
- Neue Spalte `stage_entered_at` mit Phasenhistorie: Der Server stempelt jeden Phasenwechsel; der Client schickt keine Verweildauern mehr.
- **Manager dürfen jetzt verschieben:** Bislang durften nur Admins schreiben; die RPC erlaubt `admin` und `manager` innerhalb des eigenen Mandanten.
- Kanonische Phasen sind die sieben deutschen Labels; unbekannte Phasen werden serverseitig normalisiert.
- Das Frontend liest Phasenwechsel über `crm-query-export` und schreibt über `src/features/crm/services/` — keine `sessionStorage`-Overrides mehr.

### 2. Serverseitige Qualifizierung und Deal-Konvertierung (`supabase/migrations/20261111_lead_qualification.sql`)

- Neue Tabelle `lead_qualifications` (BANT: Budget, Authority, Need, Timeline) mit RLS — Viewer lesen, `admin`/`manager` schreiben.
- Neuer RPC `convert_lead_to_deal`: atomare, genau-einmal-Konvertierung je `(organization_id, contact_id)`; `source_contact_id` verknüpft den Deal mit dem Lead-Kontakt.
- **Manager dürfen jetzt konvertieren** (siehe oben).
- Fehlerfälle serverseitig kodiert: `LP403` (Rolle), `LP404` (nicht gefunden), `LP409` (bereits konvertiert), `LP422` (ungültige Daten); Advisory-Lock gegen Race-Bedingungen.
- Bestandsdaten werden per Backfill migriert; `qualified_at` wird übernommen.

### 3. Funnel mit echten Verweildauern (Auftrag 140)

- Der Bottleneck-Alert rechnet Verweildauern ausschließlich aus dem serverseitigen `stageEnteredAt` — keine clientseitigen Schätzungen oder Browser-Speicher-Quellen mehr.
- Grenzwert 30 Tage; ein Engpass liegt nur bei Überschreitung vor.
- Deals ohne Phasendatum (vor v3.1 angelegt) werden offen gezählt und benannt: „{n} Deals ohne bekannte Verweildauer (vor v3.1 angelegt)." — sie gelten nie als Engpass. Bei komplett unbekannten Daten erscheint ein neutraler Hinweis statt der All-Clear-Meldung.
- **Bestandsdeals haben keine Verweildauer; Werte aus Browser-Speichern werden nicht übernommen.** Es gibt keine erfundenen rückwirkenden Historien.

### 4. Legacy-Dashboard entfernt (Auftrag 141)

- Das alte Executive Dashboard (Executive Cockpit V2 mit `LivePerformanceSection`) entfällt ersatzlos — samt der verwaisten `liveKpi`-Präsentationsschicht.
- Die persönliche Dashboard-Ansicht ist die einzige Variante unter `/dashboard`; `/dashboard/tiles/:tileId` bleibt erreichbar.
- Der Build-Schalter `VITE_EXECUTIVE_DASHBOARD_V2` und die komplette Rollback-Logik (CI-Rückschalt-Build, Rollback-E2E, Orchestrator-Schritte) sind entfernt.
- **Rückweg ist der Tag `v3.0.0`.**
- Der Live-KPI-**Datenpfad** (`services/liveKpi`, Live-Kacheln der persönlichen Ansicht) bleibt unverändert.

### 5. Aufräumarbeiten (Auftrag 136)

- Der tote `AIInsightDrawer` mit der falschen Aussage „Powered by LeadPilot Gemini AI Engine" ist entfernt.

## Upgrade von v3.0.0

1. **Zuerst Migrationen anwenden** (siehe Warnhinweis oben): `20261110` und `20261111` auf alle gehosteten Instanzen.
2. **Dann Edge Function deployen:** `supabase functions deploy crm-query-export` — die aktualisierte Function ist Voraussetzung für `stageEnteredAt`/`sourceContactId` im Funnel.
3. Frontend-Code aktualisieren und Produktions-Build ausrollen:
   ```bash
   npm run build
   ```
4. Keine neuen externen Abhängigkeiten, keine neuen Secrets.
5. `VITE_EXECUTIVE_DASHBOARD_V2` kann aus der Umgebung entfernt werden — der Schalter existiert nicht mehr.

---

## Rückweg

- **Vollständiger Rückweg:** Tag `v3.0.0` (Frontend + Datenbankstand). Achtung: Daten, die unter v3.1.0 serverseitig geschrieben wurden (`lead_qualifications`, `stage_entered_at`, Phasenhistorie), werden von v3.0.0 nicht gelesen — der Rollback ist damit ein Downgrade mit Datenverlust-Sicht auf neue Felder.
- **Nur Frontend:** Tagged Build von `v3.0.0` läuft gegen dieselbe Datenbank; kanonische Phasen und neue RPCs sind für v3.0.0 unsichtbar, aber nicht schädlich.
