# Rollback v2.3.0

**Dokument-ID:** OPS-ROLLBACK-230 · **Gate:** G65 (Auftrag 067S) · **Stand:** 25.09.2026

## Strategie

**Frontend zurück, Schema bleibt.** Ein Rollback stellt die vorherige Frontend-Version
bereit und lässt das Datenbankschema auf dem Stand v2.3.0 (Spec §19). Das ist möglich,
weil alle Migrationen von v2.3.0 vorwärtsgerichtet und nicht destruktiv sind. Sie
ergänzen Tabellen, Spalten, Policies und Funktionen, löschen aber keine Daten.

Ein Schema-Rückbau ist **nicht vorgesehen**. Er würde Mandantentrennung (RLS) und
Audit entfernen. Muss das Schema doch zurück, gilt nur der Weg über das Backup aus
dem Runbook (Abschnitt 3), mit Datenverlust seit dem Backup.

## Ablauf

1. Vorherige Frontend-Version bauen und ausliefern: `git checkout v2.2.0`, dann
   `npm ci && npm run build`. Bei einem Rollback innerhalb von v2.3.x den vorherigen
   Tag verwenden.
2. Edge Functions und Schema **nicht** zurückrollen.
3. Smoke-Test: Die App lädt ohne Fehler. Das v2.2.0-Frontend zeigt seine
   eingebauten Demodaten, denn Mandantendaten liefert RLS ihm nicht aus (siehe unten).
4. Ursache beheben und vorwärts neu ausrollen.

## Getesteter Nachweis (25.09.2026, lokales Supabase mit Seed)

Frontend aus Tag `v2.2.0`, gebaut mit den lokalen Supabase-Werten, gegen das Schema
v2.3.0 (alle Migrationen inklusive G65):

| Prüfung                                                                                                                                   | Ergebnis                                            |
| ----------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| Seiten `/dashboard`, `/crm/leads`, `/crm/companies`, `/crm/deals`, `/crm/live-simulation`, `/company/data-basis`                          | alle gerendert, 0 unbehandelte Fehler (`pageerror`) |
| Schreibzugriffe des Browsers während des Rundgangs                                                                                        | 0                                                   |
| Datenbestand vorher/nachher (companies, contacts, imported_funnel_deals, simulation_runs, organizations, organization_members, audit_log) | unverändert                                         |
| Anonymer Lesezugriff, wie ihn v2.2.0 nutzt (`GET /rest/v1/companies`, `contacts`, `imported_funnel_deals`)                                | `200 []`, keine Mandantendaten                      |
| Anonymer Upsert, wie ihn der frühere v2.2.0-Seeder nutzte (`POST /rest/v1/companies`)                                                     | `42501` (RLS)                                       |

Ergebnis: Das vorherige Frontend läuft gegen das neue Schema stabil. Es sieht keine
Mandantendaten und kann nichts schreiben. Das Rollback ist damit sicher, aber
funktional eingeschränkt: Die Mandanten-, Rollen- und Auditfunktionen von v2.3.0
fehlen, solange das alte Frontend ausgeliefert ist.
