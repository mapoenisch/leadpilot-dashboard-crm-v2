# Betriebs-Runbook v2.3.0

**Dokument-ID:** OPS-RUNBOOK-230 · **Gate:** G65 (Auftrag 067S) · **Stand:** 25.09.2026

Dieses Runbook beschreibt, wie LeadPilot Dashboard-CRM v2.3.0 auf einem
Supabase-Projekt aufgesetzt oder von v2.2.0 aktualisiert wird. Das Repository
enthält keinen Deploy-Provider. Der Frontend-Build ist ein statisches Bundle
(`dist/`), das jeder statische Hoster ausliefern kann.

## 1. Konfiguration

### Frontend (Build-Zeit, `.env` bzw. Umgebung des Build-Servers)

| Variable                 | Pflicht | Inhalt                                                                               |
| ------------------------ | ------- | ------------------------------------------------------------------------------------ |
| `VITE_SUPABASE_URL`      | ja      | Projekt-URL, `https://<ref>.supabase.co`                                             |
| `VITE_SUPABASE_ANON_KEY` | ja      | öffentlicher anon-/publishable-Schlüssel, **nie** der service_role-/secret-Schlüssel |

Ein Produktivbuild läuft **nur** mit `npm run build:production`. Die Prüfung
`scripts/checkProductionConfig.mjs` bricht vor dem Build ab, wenn ein Wert fehlt,
noch Platzhalter aus `.env.example` enthält, nicht `https` nutzt oder ein
privilegierter Schlüssel im Browser landen würde. `npm run build` ohne Werte
erzeugt bewusst den Demo-Modus für Entwicklung und CI und ist **kein** Produktivbuild.

### Edge Functions (Function-Secrets im Supabase-Dashboard bzw. `supabase secrets set`)

| Secret                                      | Function          | Pflicht                   | Verhalten ohne Wert                                |
| ------------------------------------------- | ----------------- | ------------------------- | -------------------------------------------------- |
| `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` | alle              | ja (von Supabase gesetzt) | Antwort 500 `…_NOT_CONFIGURED`                     |
| `LEADPILOT_INGEST_SECRET`                   | `live-kpi-ingest` | ja                        | 500 `INGEST_NOT_CONFIGURED`, kein Event angenommen |
| `SITE_URL`                                  | `manage-members`  | empfohlen                 | Einladungslinks zeigen auf `http://127.0.0.1:4321` |

Secrets gehören nie ins Repository. `.env.example` ist die einzige Vorlage.

### Auth

- E-Mail-Login aktiv, **öffentliches Sign-up deaktiviert** (Spec §20). Neue Mitglieder
  entstehen nur per Admin-Einladung (`manage-members`).
- `Site URL` und `Redirect URLs` in Supabase Auth auf die Frontend-Domain setzen.

## 2. Free-Tier-Grenzen

v2.3.0 ist Free-Tier-first (Spec §1). Auf dem Supabase-Free-Tier gilt:

- Das Projekt wird nach längerer Inaktivität pausiert. Der erste Aufruf danach
  scheitert, bis das Projekt im Dashboard fortgesetzt ist.
- Es gibt **keine automatischen Backups** und kein Point-in-Time-Recovery. Vor jeder
  Migration ist das manuelle Backup aus Abschnitt 3 Pflicht.
- Datenbankgröße, Edge-Function-Aufrufe, Auth-E-Mails und Log-Aufbewahrung sind
  kontingentiert. Die aktuellen Werte stehen in der Supabase-Preisübersicht und im
  Projekt-Dashboard unter „Usage“; sie ändern sich und sind hier bewusst nicht fest
  eingetragen.
- Auth-Mails über den eingebauten SMTP-Dienst sind stark limitiert. Für mehr als
  gelegentliche Einladungen einen eigenen SMTP-Anbieter hinterlegen.

Für einen Betrieb mit echten Daten empfiehlt die Spec Supabase Pro (automatische
Backups, keine Pausierung, längere Logs). Das ist nicht Teil der Abnahme von v2.3.0.

## 3. Backup vor jeder Migration

```bash
supabase db dump --db-url "$DB_URL" -f backup-schema-$(date +%F).sql
supabase db dump --db-url "$DB_URL" --data-only -f backup-data-$(date +%F).sql
```

`DB_URL` ist die Verbindungszeichenkette aus dem Dashboard (Session-Pooler oder
direkt). Beide Dateien außerhalb des Repositorys aufbewahren. Alle Migrationen
von v2.3.0 sind vorwärtsgerichtet und nicht destruktiv, trotzdem gilt: kein
Migrationslauf ohne frisches Backup.

## 4. Rollout-Reihenfolge

1. **Backup** nach Abschnitt 3.
2. **Schema und Policies:** Das Basisschema liegt als `supabase/schema.sql` im Repo und
   ist keine versionierte Migration. Vor dem Push als früheste Migration bereitstellen,
   danach wieder entfernen (wie in der CI, `docs/operations/ci-e2e-backend.md`):
   `cp supabase/schema.sql supabase/migrations/20260101000000_base_schema.sql`.
   Dann `supabase link --project-ref <ref>` und `supabase db push`. Bei einem Upgrade von v2.2.0 ist `--include-all` nötig, weil
   Migrationen mit älterem Zeitstempel (`20260100000000_…`, `20260101000000_…`) vor
   den bereits bekannten Live-KPI-Migrationen einsortiert sind. Vorher mit
   `supabase db push --dry-run --include-all` die Liste prüfen.
3. **Serverpfade:** `supabase functions deploy live-kpi-ingest manage-members crm-query-export`
   und die Secrets aus Abschnitt 1 setzen.
4. **Demo-Mandant:** entsteht durch die Migration `20260920_demo_bootstrap.sql`
   (idempotent, beliebig oft ausführbar).
5. **Ersten Admin anlegen:** Benutzer in Supabase Auth anlegen und per SQL als
   `admin` in `organization_members` der gewünschten Organisation eintragen. Weitere
   Mitglieder lädt dieser Admin in der App ein.
6. **Frontend:** `npm ci && npm run build:production`, `dist/` ausliefern. Die
   Sicherheitsheader aus `public/_headers` beim Hoster übernehmen.
7. **Smoke-Test** nach Abschnitt 5.
8. **Freigabe** im BUILD_LOG dokumentieren.

## 5. Smoke-Test nach dem Rollout

- `/login` lädt, Anmeldung mit dem Admin gelingt, `/dashboard` erscheint.
- `/admin/health` zeigt Datenquelle und Frische ohne Fehler.
- `/crm/leads` zeigt nur Datensätze der eigenen Organisation.
- `/crm/live-simulation`: Ein Admin startet einen Run, der nach Reload in der
  Run-Historie steht. Ein Viewer sieht „Runs: nur Lesezugriff“.
- `/admin/audit` listet Mitgliederänderungen und Run-Steuerung ohne E-Mail-Adressen.
- Anonymer REST-Aufruf auf `companies` liefert `[]`.
